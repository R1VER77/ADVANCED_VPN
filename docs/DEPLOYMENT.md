# Managed Linux deployment

Build and staging are separate from activation. No cloud resource or billing change is performed by these tools. No host VPN, firewall, route or DNS change occurs until an operator explicitly runs `connect`/`guard` or enables the units.

## Trust and enrollment

The operator signs flat, bounded ZIP enrollment bundles. Import verifies Ed25519 signatures, all content hashes, role/schema/path restrictions and the exact allowed role files before creating a new private enrollment directory. Files cannot introduce controller PID files, scripts, arbitrary paths or unsigned extras. The operator public key must arrive over an independently authenticated channel; a signature does not make an attacker-supplied first-use public key trustworthy.

Every device generates its own private keys (`avpn request`), and they never leave that device. The relay generates only outer QUIC and WireGuard keys, never an inner identity; the owned exit generates only its inner identity. Requests and bundles carry public data only. The single shared secret, the WireGuard PSK, is encrypted to the client and to the relay with hybrid X25519 + ML-KEM-768. The operator signs the whole enrollment set once: an Ed25519 assertion from the Nitrokey FIDO2 credential, which needs the PIN and user presence and can't be exported, plus an ML-DSA-65 signature from an operator key sealed under that credential. `operator.pub` is a JSON file naming both halves. No CA private key exists.

Managed TLS validation uses pinned SPKI device identities with WebPKI-compatible trust anchors. Fresh self-issued leaves retain the exact enrolled key, subject/SAN and TLS policy. Their validity is bounded to twelve hours; rotation occurs every six hours without online CA secrets. The device public-key pin is durable until explicitly revoked; bootstrap-anchor validity dates are not an identity-expiry mechanism. Device certificates and their TLS 1.3 handshake signatures are ML-DSA-65 only; peers presenting any other signature algorithm are refused even when pinned. Operator bundles are signed with Ed25519 and ML-DSA-65 and both must verify; `operator.pub` is the 1984-byte concatenation of the two public keys.

## Client modes and kill switch

Application mode automatically creates `avpn-app`, with only loopback and `avpn0`, default-drop nftables and private resolver mounting. Applications run as the invoking sudo user's UID/GID. Proxy variables and common Firefox remoting/DBus variables are cleared. This does not fully sandbox hostile filesystem/desktop IPC; use a fresh browser instance/profile and do not delegate networking to an existing host process.

Whole-device mode changes the host's IPv4 default route and resolver. When `/etc/resolv.conf` is generated by a running systemd-resolved, the controller does not rewrite it; it sets `10.77.0.1` with routing domain `~.` on `avpn0` through `resolvectl`, so every name is resolved through the tunnel, and resolved discards these settings when the link is removed. Otherwise the file is replaced and the original restored by `reset --allow-cleartext`. Its output policy allows only loopback, restricted bootstrap DHCP, the WireGuard endpoint for the dedicated service UID, outer QUIC over the carrier for that UID, and IPv4 traffic through the inner TUN. Direct DNS and IPv6 escape are blocked. Do not activate this over a conflicting existing VPN or without a local/out-of-band recovery console. It was tested only in a disposable network namespace, not enabled on the laptop.

Disconnect/crash leaves nftables, interfaces and namespace isolation in place. Data-plane children receive a parent-death SIGKILL, no capabilities and no-new-privileges. The supervisor recreates failed children under the guard. Only explicit `reset --allow-cleartext`, with the controller stopped, removes the project's guard and restores recorded defaults/DNS. Existing protected app processes prevent namespace teardown.

The managed service deliberately shares the administrative mount namespace so named network namespaces remain visible to independent CLI launches and survive controller death. Do not add systemd options that implicitly create private mount namespaces without redesigning handle distribution. The local-only supervisor has a restricted capability set; network-facing children drop the entire capability bounding set. Cgroups bound memory, swap, CPU, tasks and FDs.

## DNS, DAITA, MTU and limits

The owned exit forwards UDP/TCP DNS to a TLS-authenticated upstream over TLS 1.3 whose only key exchange is the hybrid post-quantum group X25519MLKEM768. An upstream that cannot negotiate it receives no query: DNS fails closed, never falls back to classical key exchange or plaintext (`the_upstream_must_offer_hybrid_post_quantum_tls`). Production defaults to Cloudflare, numeric `1.1.1.1:853` with hostname `one.one.one.one` and bundled WebPKI roots. Quad9, the earlier default, offered no hybrid group on DNS-over-TLS when checked (12 Nov 2026), and with it as upstream the forwarder answers nothing; Google (`8.8.8.8:853`, `dns.google`) also works. Upstream connections are reused (RFC 7858): up to four idle connections, each closed after 20 s idle, so a lookup costs one round trip instead of a new TCP connection and post-quantum TLS handshake; a reused connection the upstream has closed is replaced and the query retried once. Measured over a 308 ms path: median lookup 1.4–1.8 s before, 0.31 s after, and 36–39 of 40 lookups answered before against 40 of 40 after. Queries are not logged or persisted. This is not an independent DNSSEC validator, content-filtering system or DNS anonymity service.

GotaTun's actual DAITA engine supplies constant-size nonempty data padding and Maybenot-driven decoys/shaping. `balanced` uses NetFlow padding and FRONT re-armed for every burst; `strong` adds Tamaraw with a stop machine that rounds every trace on its constant clock (`src/daita.rs`). These are not Mullvad's private/current production defenses. Classifier resistance was measured, not inferred from observing padding: `docs/evidence/DAITA_LAB.json` (`tools/daita_lab.py`, `tools/wf_attack.py`). Empty WireGuard keepalives and handshakes are observable control traffic. `strong` (Tamaraw) is constant-rate shaping and measured about 0.34 Mbit/s; `balanced` measured about 290 Mbit/s.

Every hop bounds each session at 100,000,000 bytes/s and 100,000 packets/s, the maximum the configuration allows. The earlier 2 MB/s and 2,000 packets/s bound capped the tunnel at about 10 Mbit/s and dropped bursts, which forced TCP retransmissions. CI fails if the namespace benchmark falls below 50 Mbit/s.

No daily cap or carrier rate limit is applied by default. An operator can opt in with `preferences --daily-limit-mib N` (1..10240). With a cap, kernel quotas meter the carrier in grants of up to 64 MiB reserved durably before launch; when the carrier stops under supervision the uncounted remainder is refunded, so restarts do not consume the allowance. Clock rollback blocks new grants. Exhaustion stops the carrier, never DAITA; the supervisor stays running and blocked (it does not exit, so the service never ends silently) and resumes at the next UTC day or after the cap is raised. A supervisor crash keeps its grant reserved (over-counting, never under-counting). `--no-daily-limit` removes the cap.

The managed IPv4 underlay must support MTU >=1420. WireGuard MTU is 1340, outer QUIC UDP payload 1280, inner QUIC UDP payload 1200 and inner IP MTU 1100. IPv6 is deliberately blocked, not forwarded. Dynamic path-MTU fallback is not implemented. A failed or incompatible path remains blocked.

## Activation and recovery

Stage with `tools/install.py --out NEW_DIRECTORY`. `--apply` requires root, installs under `/opt/advanced-vpn`, creates the hash-locked Python environment and installs service files; it refuses to overwrite an existing installation and never enables the VPN. Review the staged manifest and signed source first.

After role enrollment, use `avpn connect` for a foreground managed session. Save `preferences --mode whole-device` only if this is the intended whole-host VPN. Then an operator can explicitly enable both managed units. The guard is ordered before normal network services; actual boot ordering, initramfs traffic, DHCP, NetworkManager and recovery-console behavior require validation on the target OS.

Nitrokey-protected devices need the PIN and a touch at cold start, and there is no unattended bypass. The PIN source depends on context. A terminal reads it with no echo. Under systemd, the `advanced-vpn.service` unit, including at boot in whole-device mode, uses `systemd-ask-password` without `--keyname` or `--accept-cached`, so nothing is cached in the kernel keyring. That prompt is answered at the boot console or with `sudo avpn unlock`, which runs `systemd-tty-ask-password-agent --query`. A desktop session falls back to `pinentry-gnome3`. An unanswered prompt times out after 300 s, the unit restarts and asks again, and the guard holds throughout. `systemd-creds` devices decrypt at service start: with the TPM2 when present, otherwise with the host credential key, which only helps if the disk is encrypted. To recover from a lost device or token, run `request` → `init` → `enroll` again; no key backups are kept. Rotate compromised device identities by delivering a newly signed enrollment under the persistent guard; do not edit pins or silently accept unknown keys. A coordinated multi-device key-revocation/update service is not included.

No cloud deployment, live WAN test, installed-host reboot test or independent security audit has been performed for this release.

## Hop placement on free allowances

Every byte you send or receive is transmitted out of every server in the chain. So each hop's provider counts roughly your whole traffic against its egress allowance, and a free chain is only as large as its smallest allowance. Checked against the official pages and your accounts on 2026-11-08:

| Provider | Free outbound | Free compute | Notes |
|---|---|---|---|
| OCI | 10 TB a month | `VM.Standard.E2.1.Micro` ×2, Ampere A1 | E2 micro is capped at 50 Mbit/s. Idle instances (<20% use for 7 days) may be reclaimed. A tenancy has a single home region. Free micro shapes may already be in use, and A1 capacity can be unavailable. No TPM on free shapes. |
| AWS | 100 GB a month (all services) | `t3/t4g.micro/small` (free plan) | NitroTPM needs your own UEFI AMI. One selected Region per project. The `default` profile is denied EC2 in `ap-southeast-1`; check the project Region in AWS Settings. |
| GCP | 1 GB a month (from North America) | 1× `e2-micro` (US regions) | vTPM available. 1 GB is too little for a hop; anything beyond is billed. |
| Cloudflare | — | — | Can't be a hop. No free product carries UDP: Spectrum UDP is Enterprise-only, Tunnel and Workers are TCP/HTTP only. |

Suggested free chains. Different providers per hop keep any one company from seeing both ends.
- **1 hop:** an OCI exit. 10 TB, but the exit sees both ends.
- **2 hops:** an AWS relay → an OCI exit. About 100 GB a month free. Amazon sees your IP; Oracle sees destinations.
- **3 hops:** an AWS relay → an OCI middle → an OCI exit. Amazon has your IP. Oracle sees both the middle and the exit, so it can link them, but never your IP. A GCP middle would separate providers fully, but its 1 GB allowance makes it a paid hop.

Don't place hops on hosts that already run other services, unless you mean to; a hop shares that host's network and logs. `avpn cloud` creates dedicated servers.

## Hosts with their own firewall

`avpn` installs its rules in its own nftables table. It can't override another table's drop. OCI's Ubuntu images ship iptables `INPUT` and `FORWARD` chains that reject everything except SSH, and the same applies to any default-drop host firewall. On such a host, add accepts ahead of the reject:
- **Every server:** its public listening port: UDP 443 on the first hop (and 8443, where the first hop's own firewall redirects 443 for the unprivileged camouflage process), the QUIC port on later hops. WireGuard itself (41194) is reachable only over loopback.
- **First hop:** `-i avwg0 -p udp --dport 4433`.
- **Exit:** `-i avpn0 -p udp --dport 1053` and `-i avpn0 -p tcp --dport 1053` for DNS, and `FORWARD -i avpn0` and `FORWARD -o avpn0 RELATED,ESTABLISHED` for traffic.

The cloud provider's network firewall (an OCI security list or an AWS security group) needs the same listening port. Limit it to the previous hop's public IP where you can.

Cloud instances are 1:1 NATed, so the public IP isn't on the interface. Exits and middle relays therefore bind `0.0.0.0:<port>`, while the previous hop sends to the public endpoint you enrolled.

## TPM-bound keys on servers

`--protect systemd-creds` seals with `host+tpm2` whenever `systemd-analyze has-tpm2` passes, and with the host key otherwise. `protection.json` records which was used. `auto` is never used, because it silently drops the TPM when the TSS2 libraries are missing, which is the case on Debian cloud images. On Debian, install `libtss2-esys-3.0.2-0t64 libtss2-mu-4.0.1-0t64 libtss2-rc0t64` **before** `avpn request`.

On AWS, NitroTPM needs an AMI registered with `--boot-mode uefi --tpm-support v2.0`. Copy the official image into your account first (`copy-image --encrypted`), then register the copy's snapshot with those flags.

## Older distributions

Servers running Python 3.10 (Ubuntu 22.04) are supported. The hash lock carries version markers for them. Binaries must be built against the target's glibc or an older one: build in a container of the oldest target release. systemd before 250 has no `systemd-creds`: upgrade such hosts. `--protect none` (private keys as root-only plain files, readable by anyone with root or the disk) is refused unless you add `--insecure-plaintext-keys`, and `avpn doctor` flags it; use it only for tests or throwaway devices.

## Single-homed servers

The data plane's UDP sockets answer from the address the kernel routes replies
through. Give each chain server **one** address on the path clients use; a 1:1 NAT
public address (AWS, OCI) is fine. A server with two links to the internet may reply
from the wrong address, and NAT on the client's side would then drop the reply.

## Hiding your address from the first hop (upstream entry)

`sudo avpn preferences --upstream-interface IFACE` sends traffic to the first hop
only through IFACE, for example an existing VPN interface. A separate nftables table
drops anything to the first hop that would leave another way. If the upstream drops,
the first hop is unreachable rather than reached directly, and connecting with the
upstream absent is refused.

- **Point-to-point upstreams** (WireGuard, tun) need nothing more.
- **Ethernet-like upstreams** use a gateway they already route through, or `--upstream-gateway IP`.

`avpn doctor --check-egress` shows the address the first hop sees. The namespace lab
proves all three properties: the relay counts packets by source, and the upstream is
dropped and then removed. See `avpn help privacy`.

## Installed layout

`sudo python3 tools/install.py --apply [--role ROLE --protect MODE]` installs or upgrades
everything below. With `--role`, it also generates this device's keys. It links `avpn`
and `avpnctl` into `/usr/local/bin`, because `sudo` searches only system directories.

- `/opt/advanced-vpn/bin/avpn`: the command line (Rust). It renders results only.
- `/opt/advanced-vpn/bin/avpnctl`: the privileged controller, running in the hash-locked venv with `python -E -s`. The systemd units run it directly.
- `/opt/advanced-vpn/bin/avpn-cloud`: cloud setup, using the system `python3`. It runs as the user, never as root.
- `/opt/advanced-vpn/docs/cli/`: the reference pages, also compiled into `avpn help`.

A user installation (`tools/install.py --user`, for an operator machine) has the same
pieces under `~/.local/share/advanced-vpn/app`, with its venv beside it. A small
`~/.local/bin/avpn` points the command line at them. It runs no services, and as root
`avpn` still uses only `/opt/advanced-vpn`.
