# avpn-mix-lane — Implementation Notes

Status: **built, tested, byte-identical to the reference oracle.**
`cargo test` → **40/40 passing** (28 unit/property + 3 full-cell byte-identity +
3 GPA-lab simulation + 6 primitive cross-checks), zero warnings, rustc 1.100.0.

This is the option-1 build: the PQ-Sphinx option E protocol ported onto
**audited primitives**, plus the **relay mix node** (the §1.2 integration
surface the reference pack deliberately left out). The `avpn mix` production
lane keeps running Katzenpost (X-Wing headers) until this crate passes the
cutover gates — see `CUTOVER_KATZENPOST.md`.

## Verification chain (three independent layers)

1. **Primitive vectors** (`tests/vectors.rs` vs `vectors.txt`): SHA-256, HKDF,
   keyed BLAKE3, X25519, ChaCha20-Poly1305, ML-KEM-768 ek/dk/K/c/implicit-

   implementations (hashlib, blake3, cryptography, kyber-py; kyber-py is
   itself validated against the NIST KATs).
2. **Full-cell byte-identity** (`tests/cells.rs` vs `cells.txt`): given
   identical seeded randomness, this crate reproduces the reference crate's
   cells, payload keys, per-hop secrets, per-hop post-processing states, and
   SURB reply cells **byte for byte**, at v = 2..5, on a repeated-mix path
   (A,B,A), and for SURB round-trips. Regenerate with
   `tools/dump_cells.rs` (run inside the reference crate:
   `cargo run --example dump_cells --release > cells.txt`).
3. **GPA lab, simulation tier** (`tests/lab.rs`): a 6-mix network under the
   full §1.2 discipline — delivery through real delay queues and mailboxes,
   replay rejection, tagger resistance, cross-link byte-window linkability,
   Erlang delay sanity, and mix accounting closure.

## What the lab caught before it shipped (read this)

Two genuine linkability gaps in the option E design as specified — both
found by the lab's "no 64-byte window shared between two links" check, both
fixed in the reference crate and this crate together, both covered by new
tests (`r3_*`, `r4_*`, and the lab assertion itself):

- **R3 — payload re-masking (the Sphinx β-layer).** The design re-encrypts
  header slots per hop (R1) but let the ~2.7 KB payload region ride
  untouched, so colluding observers on two links of a path could byte-match
  it straight through the Exp delays. Fix: the client pre-masks the sealed
  payload with all v hop-keyed ChaCha20 streams; each hop XORs off its own
  (mixes learn nothing). SURB replies invert the direction (hops ADD masks,
  the SURB creator strips them — the replier holds no path secrets); the
  per-hop operation is identical, so no wire flag is needed. Zero size cost.
- **R4 — dead-prefix re-randomization.** R1 shifts only *downstream* slots,
  so the cover bytes hop 1 writes into slot 1 ride unchanged on every later
  link — a 1168-byte static region, again byte-matchable across an honest
  intermediate hop. Fix: hop i XORs a hop-keyed stream over the consumed
  prefix (slots 1..i−1); no MAC covers that region, so verification is
  untouched.

After R1+R3+R4, every byte of the cell except the 4-byte fixed prefix
(`version || n_hops || flags || reserved`, needed by every mix) changes at
every hop. The 4-byte residue is standard (magic/version fields) and cannot
span the 64-byte matching window.

These two findings are the strongest argument for the gate structure in
`CUTOVER_KATZENPOST.md`: the simulation lab already paid for itself before
any live traffic touched the protocol.

## Differences from the reference crate (error paths only)

Byte-level behavior is identical for all well-formed inputs. Two documented
error-path differences, both flagged for the reviewer:

1. `ml-kem` 0.2.3 does not re-run the FIPS 203 modulus check when decoding
   an encapsulation key from bytes (the reference does). Keys enter only via
   our PKI-signed gossip descriptors; restore the check upstream.
2. `ml-kem` 0.2.3 `DecapsulationKey::from_bytes` does not verify the
   embedded `H(ek)` against the embedded `ek` (their code carries an XXX
   note). Our DKs are always self-consistent.

API differences vs the reference 0.1.0 (hence reference 0.2.0):
`open_surb_reply(reply_secret, path_secrets, cell)` takes the reply-path
secrets (R3 unmasking), and `Surb` carries `path_secrets` — never serialized,
never leaves the creator.

## SWAPPABLE markers (production integration points)

- `sphinx::SphinxRng` / `sphinx::DetRng` — splitmix64, **test/vector-gen
  only**. Replace with the platform CSPRNG.
- `mix::ScheduleRng` / `mix::TestScheduleRng` — xorshift64*, **test only**.
  Back the production trait with the platform CSPRNG.
- `mix::MixNode::drain` is O(queue) per call — fine for the lab; the daemon
  should use a ready-heap (BinaryHeap keyed on `ready_at`).

## Cost profile

Per cell per mix (position-independent, §1.9): 1 ML-KEM-768 decaps (~30 µs
optimized) + (v−1) X25519 + v keyed-BLAKE3 MACs + ChaCha20 over the payload
mask + dead prefix (~2.8 KB total) — comfortably inside the design doc's CPU
budget at 1280 cells/s. The mix adds: one Exp sample, one replay-cache
lookup/insert, one VecDeque slot per cell.
